# Инструменты AI и блоки автоматизаций

Те же обработчики, что заполняют страницы, могут служить агенту AI приложения и его автоматизациям. Протокол —
[spec/protocol.md](../../spec/protocol.md): §8 (блоки автоматизаций), §8.1 (блоки модуля-программы), §9 (инструменты
AI), §13 (провайдеры моделей).

## Инструменты AI

```json
"tools": [
  { "name": "queue_list", "handler": "queues", "risk": "read",
    "description": "Queues of the server with jobs waiting, failed and workers. Use it to see whether jobs pile up." },
  { "name": "queue_retry", "title": { "ru": "Повторить задания очереди", "en": "Retry a queue's jobs" },
    "handler": "retry", "risk": "change",
    "description": "Retries the failed jobs of one queue; returns how many went back.",
    "params": [{ "key": "queue", "title": "Queue", "type": "text", "required": true, "pattern": "[a-z0-9_-]{1,40}" }] }
]
```

- Агент видит два постоянных инструмента — `module_tools` (что предлагают модули сервера) и `module_call`, — поэтому
  его список инструментов не меняется, когда модули появляются и уходят (кеш промпта сохраняется).
- `description` — всё, что читает модель, чтобы выбрать инструмент: что он делает, что возвращает, когда его брать.
- `title` (необязательно) — для людей: в подтверждении вызова написано «Модуль «Очереди»: Повторить задания очереди»,
  а не `queue_retry`.
- `risk` проходит через режим AI сервера, как любая команда: `read` — проверка, `change` — действие со службой,
  `danger` — опасное действие; пользователь подтверждает то, что требует режим. Серверы Production остаются под защитой.
- `params` проверяются (типы, `required`, `choices`, `pattern` — совпадение целиком), неизвестные ключи отбрасываются
  до запуска обработчика; секреты в ответе маскируются; длинные ответы обрезаются.
- Возвращайте компактный JSON: его читает модель, а не человек.

## Блоки автоматизаций

```json
"automation": [
  { "id": "failed_jobs", "title": { "en": "Failed jobs", "ru": "Упавшие задачи" }, "symbol": "tray.full",
    "handler": "failed_count", "risk": "read", "returns": "json",
    "params": [{ "key": "queue", "title": "Queue", "type": "text", "default": "default", "pattern": "[a-z0-9_-]{1,40}" }] }
]
```

Блок появляется в библиотеке автоматизаций в разделе «Из установленных модулей», с одним входом — **сервером** — и
своими параметрами на карточке. Он выполняется на сервере, как любой шаг автоматизации: по расписанию, без
пользователя, его журнал и итог — в истории запуска.

Обработчик получает то же, что обработчик страницы, с тремя отличиями:

- `context.automation` равен `true`, а `context.server` нет (сервер карточки — то место, где блок выполняется);
- настройки — их **значения по умолчанию**: у карточки нет настроек подключения; то, что меняется, передавайте
  параметрами блока;
- секретные настройки не передаются.

`returns` говорит, что получит следующий блок:

| | |
|---|---|
| `json` (по умолчанию) | JSON; ключи сводки дают строку блока в запуске: `{"status": "ok" \| "warn" \| "error", "summary": "3 failed", "value": 3, "unit": "jobs", "items": [{"label", "status", "value", "detail"}]}` (`message` работает как `summary`). Остальные ключи — значения, которые следующие блоки читают как `{{ in.<ключ> }}`. |
| `text`, `number`, `list` | читаются из stdout так же, как «Что вернуть» автоматизаций читает вывод команды |
| `none` | только получилось или нет |

```sh
# scripts/failed_count.sh
q=${SK_INPUT_QUEUE:-default}
n=$(php "$SK_SETTING_ARTISAN" queue:failed --queue="$q" 2>/dev/null | grep -c '^|' || true)
st=ok; [ "$n" -gt 0 ] && st=warn; [ "$n" -gt 50 ] && st=error
printf '{"status": "%s", "summary": %s, "value": %d, "unit": "jobs"}' "$st" "$(sk_json_string "$q: $n failed")" "$n"
```

Id блока в графе складывается из id модуля и id блока: автоматизация, которой поделились с тем, у кого модуль
установлен, находит блок.

### Блоки модуля-программы

Блок модуля-программы вызывает свой обработчик в программе на этом Mac (`handler/call`, протокол §8.1) — без
скрипта и без оболочки:

```json
"automation": [
  { "id": "check_urls", "handler": "check_list", "risk": "read", "server": true, "returns": "json",
    "title": { "en": "Check URLs from the server", "ru": "Проверить адреса с сервера" },
    "params": [{ "key": "urls", "type": "text", "required": true, "title": "URLs" }] }
]
```

- `input` — параметры карточки, с типами; `context.settings` — настройки модуля.
- `server: true` даёт блоку вход «сервер» (нужно право `exec`): `ctx.host.exec` там идёт через **сессии
  автоматизации** — её профиль сервера, её очередь входов; ночью код 2FA, который некому ввести, заставляет шаг ждать
  человека. Без `server` сервера нет, и `host.exec` получает отказ.
- Итог возвращайте так же, как `$SK_RESULT` серверного блока: объектом (`{status, summary, value, items: [{label,
  value, unit, status, detail}]}`) для `returns: json` или строкой для `text` / `number` / `list`. Выброшенная
  `ModuleError` завершает шаг ошибкой с её текстом.
- В окне разрешения — «программа расширения» на этом Mac, обработчик, параметры и `risk` блока из манифеста.
- «Стоп» запуска прерывает вызов (`ctx.signal`). «На сервере по cron» такой блок не выполнить (программа — на этом
  Mac): установка автоматизации на сервер получает отказ с названием блока.

Пример — `examples/http-checks` (`check_urls` — с сервера, `check_urls_mac` — с этого Mac).

## Провайдеры моделей

Расширение может быть провайдером модели (`contributes.ai`, протокол §13). В Настройки → AI появляется профиль из
него (меню «+» → «Из расширений»): название и иконка вклада, поля `fields` как настройки профиля, модели, которые
перечислит программа, уровни `reasoning`. Профиль выбирается везде, где выбираются профили: AI-панель, «Составить
запрос», AI-фильтры, автоматизации.

```json
"contributes": { "ai": [{ "id": "echo", "title": "Echo", "reasoning": ["low", "medium", "high"],
  "fields": [{ "key": "base_url", "type": "text", "title": "Address" }, { "key": "api_key", "type": "secret", "title": "API key" }] }] }
```

Программа отвечает на три своих метода:

- `ai/models` — список моделей `[{id, title}]`;
- `ai/chat` — ответ: кусочки приходят уведомлениями `ai/delta` (`text`, `tool_use`, `tool_input`, `progress`, `usage`)
  с id потока, в конце — результат `{stop, usage, model, message?}`;
- `ai/cancel` — пользователь нажал «Стоп».

```ts
defineModule({
  handlers: {},
  ai: {
    models: () => [{ id: "echo-1", title: "Echo 1" }],
    async chat(req, ctx) {
      ctx.delta({ type: "text", text: "Hello" });            // кусочки по мере готовности (ai/delta)
      // вызов инструмента: ctx.delta({ type: "tool_use", toolId: "t1", name: "list_sessions", input: {} }); return { stop: "tool_use" }
      return { stop: "end_turn", usage: { input_tokens: 10, output_tokens: 1 } };
    },
  },
});
```

- `req` — то же, что получает любой провайдер приложения: `system`, `messages` (блоки: text, tool_use, tool_result),
  `tools`, `max_tokens`, `effort` — уже после маскировки секретов и политики режима AI. `settings` и `secrets` —
  профиля: секретные поля хранятся в связке ключей этого Mac, как ключи API встроенных провайдеров, и требуют права
  `secrets`.
- Вызов инструмента, который «попросила» модель, проходит правила режима AI и подтверждения пользователя — сама
  программа инструменты не выполняет.
- `ctx.signal` прерывается, когда пользователь нажимает «Стоп» (`ai/cancel`). Выброшенная ошибка показывается как
  ошибка провайдера.
- `examples/ai-echo-provider` — предсказуемая замена без сети и настоящих моделей, с потоковым ответом и вызовами
  инструментов: печатает ответ по словам, на «проверь сервер» вызывает `list_sessions`, затем `run_command uptime`.
